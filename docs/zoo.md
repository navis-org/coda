# The Zoo

Workflows other people deposited: a public GitHub repository, a committed index, and a browser
inside Coda. `Examples ▸ Browse Workflows…`, or the command palette.

The repository is [`navis-org/coda-zoo`](https://github.com/navis-org/coda-zoo); its
`CONTRIBUTING.md` is the contributor-facing half of this document.

## Why GitHub, and which GitHub

CORS is not the constraint people expect it to be. Measured 2026-08-26:

| host                        | CORS | cache                        |
| --------------------------- | ---- | ---------------------------- |
| `raw.githubusercontent.com` | `*`  | `max-age=300`                |
| `api.github.com`            | `*`  | 60 requests per hour, per IP |
| `cdn.jsdelivr.net/gh`       | `*`  | 7 d browser / 12 h edge      |
| `navis-org.github.io`       | `*`  | `max-age=600`                |

All four are open. What separates them is everything else.

**The API is out on the quota.** Sixty requests an hour is per *IP*, so a lab behind one NAT
shares them between everybody in it, and the failure is a browser that shows an empty zoo for a
reason nobody in the building can see. It is also the only host that can list a directory, which
is why there is a committed `index.json` at all — `raw` serves files and nothing else.

**jsDelivr is out on freshness.** Twelve hours of edge cache means a merged pull request takes
half a day to appear, and a contributor cannot tell that from a rejected one.

**`raw` is unmetered and five minutes behind.** So the index is one request to raw, cached
through `data/cache.ts` at the same five minutes raw itself advertises, and a graph is fetched
when somebody opens it.

**The repository has to be public**, and that is not a preference. A private repository needs a
token on every read, and the token Coda already stores is `gist`-scoped precisely because that
scope cannot read a repository. Widening it would put "can read all your private code" behind a
button whose job is to list example workflows.

## The shape of it

```
workflows/<slug>/
  graph.coda.json     what Coda's Save button writes
  meta.json           name, summary, tags, authors, requires
  README.md           the long description
index.json            generated; the only file Coda downloads to build the list
```

`src/data/zoo/format.ts` is the contract, and it is one file on purpose: the reader
(`parseZooIndex`) and the generator (`buildEntry`, via `publish.ts`) both use it, and a generator
and a reader that disagree produce an index that passes CI and renders as nothing. That is why
the *coercions* are exported too, not only the types — "what counts as a string here" and "what
counts as a slug" are as much part of the contract as the field names, and they were briefly
written out on both sides.

The index deliberately does **not** name the repository it came from. It did, and nothing read
it: every link goes through `zooRawUrl`/`zooEntryUrl`, which take the `ZooSource` the index was
fetched from and therefore already know. A document restating where it lives is a second copy of
that fact, downloaded by every visitor, that can disagree with the one the reader used to get
there.

**The index is a pure function of `workflows/`.** `ZooIndex.updatedAt` is the newest entry's
commit date rather than a wall clock, and the entries are sorted by slug. Without that, the file
differs from itself on every run and `--check` cannot byte-compare at all.

**CI regenerates it; a contributor does not.** That is the only arrangement that terminates, and
the reason is worth writing down because the obvious one does not work. An entry's `updatedAt`
is the date of the commit that touched its directory — so an index committed *alongside* a
change carries the previous date, and a `--check` on the very next run fails on the commit that
was supposed to satisfy it. Generating after the push converges in one round instead. The commit
is made with `GITHUB_TOKEN`, whose pushes deliberately do not trigger workflows, and that is what
stops the loop. `--check` survives as a local convenience and is used nowhere in CI.

## Where the validator lives, and why it is not in the zoo

`scripts/zoo-index.ts` is in *this* repository, and the zoo's CI checks Coda out to run it.
That is a minute on every pull request, and it buys the only checks worth having: whether
`out.network` still exists, whether a param survived a rename, whether the declared `requires`
matches the dataset nodes actually in the graph. None of those are answerable from JSON alone. A
validator that cannot see the registry can check that the braces balance, and the failure it
misses is exactly the one this feature has — a workflow deposited last year that opens today
with a node silently dropped out of the middle of it.

The consequence worth stating: **the index cannot be generated by a Coda that disagrees with
it.** The zoo runs the generator weekly on a schedule, so registry drift surfaces as a red build
in the zoo rather than as a blank card in somebody's browser.

Two registration lines in that script are load-bearing and read as tidying. Without
`import '../src/nodes'` no node type is registered, every graph "fails validation" with every
node dropped, and the script reports that the entire zoo is broken. Without
`registerBuiltinSources()` the same thing happens one level in: the nodes resolve and then every
dataset node reports "Data source is not registered". `data/builtins.ts` exists because of the
second one — the set used to be four lines inside `store/graphStore.ts`, which a script has no
business importing.

## What is an error and what is a warning

An error fails the build and keeps the entry out of the index; a warning is printed and ships.
The line is whether a *reader* would be misled.

- **A `deserializeGraph` warning is an error here.** In the app it means "we saved what we could
  of your file"; in a repository it means the entry as committed is not the entry that will
  open.
- **Inference errors and warnings are both errors**, the same bar `examples.test.ts` holds the
  bundled examples to. A zoo entry is documentation, and "it mostly works" is not something a
  reader can evaluate from a card.
- **A param the node no longer declares is a warning.** This is the drift detector:
  `deserializeGraph` keeps params verbatim, so one survives a load silently, does nothing, and
  leaves a workflow that looks configured and is not. A warning rather than an error because the
  usual cause is a rename with a working default on the other side, and losing somebody's
  workflow over that is worse than saying so.
- **A summary over 140 characters is an error.** The card gives it one line, and a paragraph
  pasted there is not wrapped into more room — it is cut off mid-sentence. Refused where the
  author can still fix it.
- **`requires` is compared, not derived.** Deriving it would always be right and would teach a
  contributor nothing. Comparing turns "I did not realise this needed a CAVE token" into a failed
  check with the answer in it, while the workflow is still in somebody's head. It is the one
  field where the redundancy is the feature.

## The card art

A minimap of the workflow, drawn client-side from a layout digest in the index — `[x, y, type]`
per node and index pairs for the wires.

The alternative was `startCards.ts`'s `tileNode`, which picks the last visualisation node and
draws its category glyph. That is right for five cards beside five different pictures. It fails
at a hundred community workflows, where most chains end in a table or a network plot and the
list becomes rows of the same icon. A minimap is recognisable in the way minimaps are: you
cannot read it, but a two-branch join, a long linear chain and a fan-out are visibly different,
and that is what is worth seeing before opening somebody else's document.

Three decisions inside it that look like details:

- **Notes are excluded.** A workflow's text notes span several columns above and below the
  pipeline. Inside the bounds they squeeze the actual chain into a thin band and the card becomes
  mostly empty rectangle.
- **The node type travels, not its category.** The generator would need the registry to know that
  `out.network` is a visualisation; the renderer has it already. So the string crosses as-is and
  the tint resolves at draw time — which is also what makes an unknown type draw as a dashed
  hollow box rather than vanish. That is registry drift made visible, and it should be.
- **Coordinates are raw and rounded, not normalised.** Only the renderer knows the aspect ratio
  of the box it is fitting them into, and normalising two axes independently at generation time
  bakes in a distortion no reader can undo.

## Opening one

Master–detail rather than a list that loads on click, which is a deliberate departure from the
obvious reading of "clicking an entry opens it". Opening replaces the canvas and resets the undo
history, and the two questions a reader has first — what does this do, and what will it ask me
for — are not answerable from a name and one line. So a click selects, the panel answers both,
and Enter, a double-click and the button all open.

Everything past that is the path a share link already takes, and none of it is new:
`deserializeGraph` validates and drops, `loadGraph` schedules only the *cheap* pass, and
`core.tableFromUrl` — the one node that fetches a URL written into a document — is `expensive`.
So a downloaded workflow fetches nothing of its own until somebody presses Run. See
[persistence.md](persistence.md), which reasons this out for share links and pins it in
`store/shareLoad.test.ts`.

The README renders through `MarkdownView` **without** `extended`, so no fences, no tables and no
images. Same rule a dataset blurb from a Custom node gets and for the same reason: a deposited
README is written by whoever opened the pull request, an image in one is a tracking pixel, and a
fence is a directive some renderer may act on. See the `parseMarkdown` note in `CLAUDE.md`.

## Failure is a state, not an absence

This is the one surface in Coda that cannot work offline, so all three cases are drawn:

- **A stale cached copy is shown with its age** — "showing a copy from 3h ago, which may be
  missing newer workflows". A month-old list of workflows is worth a great deal more than an
  error page, and the age is what stops it being a lie.
- **A failure with nothing in hand names both causes** — unreachable host and cross-origin
  refusal, which a browser reports identically as an opaque `TypeError`. That is `data/fetchText.ts`,
  shared with the share-link resolver rather than copied from it: the function carries a comment
  warning that two functions of one name two directories apart is a grep hazard, and the zoo
  briefly made that warning come true.

- **A failed *refresh* over a list already in hand does not take the list away.** The rows are
  still the best answer available, so the failure goes to the footer beside the age and the list
  stays. Only a failure with nothing to show replaces it.
- **A dropped entry is counted and named** in the footer, with the reasons in a tooltip. An entry
  is somebody's contribution, and one contributor's mistake must not be everybody's empty list —
  but nor should it be silent, because the only way anybody finds out is if the browser says so.

## Adding a second zoo

`ZooSource` is `{ repo, ref }` and every function takes one, defaulting to `DEFAULT_ZOO`. Nothing
in the UI exposes that yet. If a lab wants its own, the shape is there; what is missing is a
place to put the setting and a decision about whether an arbitrary repository in that field
should ask the host-confirmation question `share/resolve.ts` asks for a bare `https://`. It
should.
